# Экспорт каталога со старого магазина (maniagroup.com.ua) — пояснительная записка

**Статус: экспорт сохранён в файл, в рабочую БД ничего не записано.**
Дата экспорта: см. `data/wp-import.json` → поле `exportedAt`.

## Зачем

На `maniagroup.com.ua` живёт старый WordPress/WooCommerce-магазин с полным
каталогом — 2705 товаров (одежда, обувь, аксессуары; парфюм/ароматы
исключены, см. ниже). Задача — аккуратно вытащить всё это и адаптировать под
структуру новой (текущей) базы, **не трогая** то, что уже есть в проде,
чтобы позже одной командой можно было импортировать.

## Откуда берутся данные

**WooCommerce Store API** — публичный, только для чтения, без ключей и
паролей:

```
https://maniagroup.com.ua/wp-json/wc/store/products?per_page=100&page=N
```

Это официальный, штатный API самого WooCommerce (не взлом и не парсинг
HTML-страниц). Отдаёт постранично (100 шт/страница, всего 28 страниц) чистый
JSON с полным набором полей: название, цена, фото, категории, атрибуты
(размеры), краткое и полное описание.

Проверено вручную через `curl` перед тем, как писать скрипт — заголовок
ответа `X-WP-Total: 2756` сразу дал точное число товаров в магазине.

## Что откуда берётся (маппинг полей)

У каждого товара в WooCommerce есть `short_description` — блок вида:

```
• КОД ТОВАРА: 27145 • БРЕНД: KOCCA • АРТИКУЛ: P26PTR8463ABUN 30005
• СТРАНА: Италия • СОСТАВ: 98% хлопок, 2% эластан • СЕЗОН: Весна-Лето
• ЦВЕТ: Бежевый • РАЗМЕРЫ: L| M
```

Этот блок присутствует **у 100% товаров** (проверено на всех 2705) и почти
1:1 ложится на нашу структуру:

| WooCommerce (short_description) | → наша колонка (`products`) |
|---|---|
| КОД ТОВАРА | `sku` |
| БРЕНД | `brand` |
| АРТИКУЛ | `factory_article` (настоящий артикул производителя) |
| СТРАНА | `country` |
| СОСТАВ | `composition` |
| СЕЗОН | `season` |
| ЦВЕТ | `color` |
| РАЗМЕРЫ + WooCommerce-атрибут `pa_size` | `product_variants` (по строке на размер) |

Остальные поля — из основной структуры JSON-ответа API, не из текста:

| WooCommerce (JSON) | → наша колонка |
|---|---|
| `name` | `name` |
| `permalink` (последний сегмент URL) | `slug` |
| `categories[]` — корень (`zhenskoe`/`muzhskoe`/`detskoe`) | `gender` |
| `categories[]` — самая специфичная не-брендовая, не-зонтичная категория | `category`, `category_slug` |
| `prices.regular_price` / `sale_price` (копейки → делим на 100) | `regular_price`, `sale_price`, `price` |
| `on_sale` | признак наличия `sale_price` |
| `images[]` | `image_src` (первое фото) + `images` (все) |
| `description` (HTML, очищен от тегов) | `description` |
| `is_in_stock` | `is_in_stock` |
| `attributes[].terms` где `taxonomy = pa_size` | список размеров → `product_variants` |

### Пол (gender) — как определяется

Основной способ: ищем в списке категорий товара корень `zhenskoe` /
`muzhskoe` / `detskoe` (или slug, начинающийся на `zhensk-`/`muzhsk-`/
`detsk-`).

Резерв: если категории не дали пол (7 товаров — сумки LANCASTER, вещи J.B4,
KOCCA без категории-корня), ищем слово «жіноч»/«женск», «чолов»/«мужск»,
«дитяч»/«детск» прямо в названии товара.

Результат по всем 2705: **1819 женских / 886 мужских / 0 без пола** —
каждому товару пол определён однозначно.

### Категория (type) — как определяется

У товара обычно 4-5 категорий сразу (бренд, пол-корень, широкая группа типа
«Жіночий одяг», конкретный тип типа «Жіночі джинси», иногда ещё
маркетинговая «Каталог жіночого…»). Берём **самую специфичную**, отбросив:
- категорию, совпадающую с брендом (`kocca`, `ea7` и т.д.)
- «зонтичные» категории (`zhenskaya-odezhda`, `aksessuaryi`, `obuv` и
  похожие — слишком общие, не несут информации о типе товара)

## Что исключено — парфюм

По вашей просьбе **не импортируем** ароматы Millefiori Milano (диффузоры,
сменные блоки, интерьерные духи, ароматические саше) — **51 товар** из 2756.
Определяется по категориям (`millefiori-milano`, `aromatizatory`,
`aromadiffuzory` и т.п.) или по бренду «Millefiori» в описании.

## Изоляция от текущей базы (главное требование)

Ничего из импортируемого **не может пересечься** с тем, что уже есть в
рабочей базе:

1. **ID = WP-id + 90 000 000.** Например, товар с id `85679` в WordPress
   получает id `90085679` у нас. Оригинальный WP-id всегда восстановим:
   `id - 90000000`. Коллизия с существующими товарами физически невозможна,
   пока в базе меньше 90 миллионов строк.
2. **`status = 'draft'`, `moderation_status = 'pending'`,
   `ever_published = false`.** Витрина магазина показывает только
   `status = 'publish'` — значит, импортированные товары **не появятся на
   сайте**, пока их вручную не одобрят через очередь модерации в админке.
3. **Полный откат одной командой** (если что-то не понравится после
   импорта): `DELETE FROM products WHERE id >= 90000000;`

## Фото и размеры — как это будет работать

- **Фото** — у 2703 из 2705 товаров. Ссылки на фото остаются внешними (на
  `maniagroup.com.ua`), при импорте отображаются сразу же (сайт живой). Уже
  существующий в проекте механизм `lib/photoStore.ts` (админка → «Фото»)
  скачивает их локально в `public/catalog/<id>/` — так же, как это уже
  работает для остальных товаров, отдельного кода писать не пришлось.
- **Размеры / торговые позиции** — у 2702 из 2705 товаров. Публичный
  WooCommerce API отдаёт **названия** размеров (`M`, `42`, …), но **не
  отдаёт остатки** по размерам (это закрытая часть API, нужны ключи
  `wc/v3`, которых нет). Поэтому каждый размер станет строкой в
  `product_variants` с `stock_qty = 0` — позиция появится, но с нулевым
  остатком, пока не будет отдельного прохода за реальными остатками.

## Где что лежит

- **Скрипт:** `scripts/import-from-store-api.mjs` — весь код экспорта +
  адаптации + (для будущего шага) записи в БД, с подробными комментариями в
  начале файла.
- **Сохранённые данные:** `data/wp-import.json` (≈8 МБ, 2705 товаров).
  Добавлен в `.gitignore` — это сырые бизнес-данные, не исходный код, в git
  не коммитится.

## Как это было сделано — по шагам

1. Проверили `maniagroup.com.ua` на WordPress/WooCommerce, нашли открытый
   Store API, узнали точное число товаров (`X-WP-Total: 2756`).
2. Разобрали структуру одного товара вручную (`curl` + `python3 -m json`) —
   поняли форму `short_description`, `categories`, `attributes`, `prices`.
3. Проверили существующую инфраструктуру проекта (`lib/photoStore.ts`,
   старый `scripts/import_catalog.py`, схему таблиц `products` /
   `product_variants` в `lib/pg.ts`), чтобы не изобретать велосипед и не
   расходиться со сложившимися соглашениями.
4. Написали `import-from-store-api.mjs`, прогнали **сухой прогон** (`--dry-
   run`) сперва на 40 товарах, затем на всех 2756 — без единой записи в БД,
   только для проверки маппинга.
5. По дороге нашли и поправили 2 бага на полном объёме (не видны на
   маленькой выборке): нестандартные `images`/`categories` у части товаров
   ловили `TypeError`; резервное определение пола по названию не работало
   из-за особенности `\b` в JS-regex с кириллицей.
6. По вашей просьбе исключили парфюм Millefiori (51 товар).
7. По вашей просьбе **убрали запись в БД** из режима по умолчанию —
   переписали скрипт так, чтобы результат по умолчанию сохранялся **только
   в файл** (`data/wp-import.json`), а запись в Postgres стала отдельным
   явным шагом (`--write-db`), который пока не запускался.
8. Запустили финальный экспорт всех 2705 товаров (после фильтра парфюма) —
   файл сохранён, проверена целостность JSON и совпадение количества.

## Как запустить импорт в БД, когда решите

Сейчас — ничего запускать не нужно, всё уже сохранено в файле. Когда будет
решение импортировать по-настоящему (нужен доступ к `DATABASE_URL`, он есть
только на VPS):

```bash
set -a; . /opt/maniagroup/.env.local; set +a
node scripts/import-from-store-api.mjs --write-db
```

Скрипт прочитает `data/wp-import.json` и запишет все 2705 товаров как
изолированные черновики (см. раздел «Изоляция» выше). Откат — одна строка
SQL, приведена там же.
